# LINE登録の確認番号自動送信 — 公開前候補

登録コードを本人のLINEから受け付けた直後、同じLINEへ6桁の確認番号を送ります。番号を読んでから元のブラウザへ戻るため、通常の登録で「確認番号をLINEに送る」の操作と2回目のLINE訪問を省けます。初期設定は無効です。このローカル候補の完成は、公開版への反映・本番送信を意味しません。

## 保持する境界

- Googleのログインと権限許可、店舗の選択、利用条件への同意は本人が行います。
- 自動送信は有効な署名付きWebhookからの個人トーク・テキスト登録コードのみ。コードは15分・単回で、店舗世代と生存する同じ所有者のブラウザセッションを確認します。
- PINはハッシュのみ保存し、同じブラウザ・店舗世代で5分以内、最大5回まで照合します。受信・送信成功だけではLINE確認済みや稼働中へ移しません。
- 自動と手動の送信を合わせて1分1回・1日3回、既存の共有LINE送信予算を使います。無料枠を増やす・課金する変更はありません。枠不足/不明では保留します。
- 同時クリック・重複Webhookの再送を抑止します。送信状況のGET、再読み込み、戻る操作は送信しません。結果不明は既存の保守的な予約を保持し、有効な届いた番号は照合できます。再送は本人が明示して新しいPINを作ります。
- 再発行・切断が最終送信判定より前なら送信を取消し予約を解放します。判定直後に外部APIへ渡ったリクエストは取消せないため、古いメッセージが遅れて届く可能性は残ります。そのPINは世代変更後の照合に使えません。

## 戻す場合

動作を元に戻す第一手段はフラグを`false`/未指定にすることです。既に受け付けた送信は取消しません。手動の番号送信・同一ブラウザ照合を確認します。コードも戻す場合は直前の承認済みWorker版へ戻し、追加テーブルは残します。既存`line_checks`スキーマを維持しているため、テーブルを削除してロールバックする必要はありません。復帰後に残る既存送信予算を確認し、未知の送信の予約を強制解放しません。

## 証拠と限界

native workerd + ローカルD1、署名検証、架空Google/LINEを使ったブラウザテストで確認しています。実Google認可、実LINE送信、スマートフォン実機/LINE内ブラウザ切替、印刷コピー後のQR、実利用時間は未確認です。Webhookではコード受理と既存の後続操作を順に済ませた後、PIN送信を同時最大3件で監督します。quotaとpush通信は各既存タイムアウトに加えリクエスト共通の20秒期限で中止し、期限後の未送信分は記録して手動復帰へ回します。D1障害等で途中終了した場合は90秒の送信リース後に結果不明として手動復帰します。検出と送信記録の間の画面待機も90秒で打ち切り、再送の補助へ進みます。確認番号の自動再送は行いません。

背景処理の30秒は同じリクエストの全`waitUntil`で共有されます。1イベントに20秒ずつ待つ構成を避け、遅いPIN送信が後続イベントの受理を止めないようにしています。[Cloudflare実行期限仕様](https://developers.cloudflare.com/workers/runtime-apis/context/#waituntil)

LINEのAPI受付と実到達は異なります。タイムアウト/5xxは送信済みの可能性があり、同じ試行のUUIDを`X-Line-Retry-Key`へ渡す既存senderを使います。この候補は結果不明の自動再試行を追加しません。[LINE公式の再試行仕様](https://developers.line.biz/en/docs/messaging-api/retrying-api-request/)

新しい送信記録は`line_links`の削除・再発行に連動して削除します。D1の外部キーと`ON DELETE CASCADE`に従います。[D1外部キー仕様](https://developers.cloudflare.com/d1/sql-api/foreign-keys/)
