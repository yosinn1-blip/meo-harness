# MEO Harness — 自己登録と AI 向け導入案内

日付: 2026-09-27

状態: 設計案・本人レビュー待ち（実装・公開の完了を意味しない）

分類: Architectural / 一般利用者の認証・店舗所有関係を追加する変更

## 1. 合意した目的

記事を読んだ店主が、運営者との個別のやり取りなしに、Google の店舗と LINE を接続して利用開始できるようにする。
AI に案内や設定補助を頼む人も、同じ公式手順を辿れるようにする。
美容院での試用は並行して進め、導線の実装開始を試用終了まで待たせない。

本人の「ok」は、この目的と「通常登録＋AI 向け案内」を先に整える方針への承認。
本書の具体的な構成、実装計画、本番公開、外部設定変更への承認とは分ける。

### 利用者から見た完成条件

1. 記事から「利用開始」に進める。
2. Google にログインして権限を確認し、管理できる店舗を選べる。
3. 共有 LINE ボットに自分の通知先を登録できる。
4. 接続テストと、サービスの制限・停止方法を確認して開始できる。
5. 閉じた画面を後から開いて続きができ、失敗時に次の操作が分かる。
6. 新着口コミがなければ、その旨を表示する。架空口コミを実店舗に投稿しない。
7. 利用開始だけで返信を公開しない。口コミごとの明示承認を維持する。

## 3. 選択肢と採用案

| 案 | 利点 | 問題 | 判断 |
|---|---|---|---|
| A. 運営者の共有サービスに自己登録 | 店主に開発者用キーや設置作業を求めず、記事から開始できる | 利用者認証、店舗分離、共有枠管理が必要 | 今回の主経路 |
| B. AI に自前環境への設置を手伝ってもらう | 自分のコード・環境で運用できる | 自前の GBP API 申請、LINE 等の設定が残り即時利用とは違う | 手順と条件を併記。全自動設置は今回対象外 |
| C. 現在の相談・管理者招待を半自動化 | 既存の試用手順を維持しやすい | 招待受諾や店舗と依頼者の照合が残り、自己登録の完成条件を満たさない | 美容院試用の既存経路として維持 |

**A を実装対象とし、AI 用の案内も A を既定にする。**
「AI を使う人なら自分で設置するはず」とは決めつけない。
公開範囲は上限付きの試用。無制限・永久無料を約束する設計にはしない。

## 4. 利用画面と状態

### 4.1 新規利用

1. `/start`：仕組み、投稿前承認、料金・上限、権限、停止方法、データ取り扱いを表示。
2. 「Google で接続」：本人が Google 画面で認可する。パスワードは本サービスにも AI にも入力させない。
3. 店舗選択：Google API がその利用者に返した店舗だけを表示。1 店舗なら候補を選択済みにするが、店名を確認してもらう。
4. LINE 登録：友だち追加 URL・QR、期限付きの登録コード、コピー操作を表示。
5. LINE 側でコードを送るとブラウザに「LINE を検出」。この時点では自動運用を始めない。
6. 接続確認：テスト通知を明示操作で送り、LINE に届く確認番号をブラウザに入力して通知先を確定。その後で利用開始を確認する。
7. `/account` に移り、稼働状態、最終確認時刻、通知状態、残り利用枠、停止ボタンを表示。

初期対象は 1 Google 利用者につき 1 店舗・1 LINE 通知先。代理店の一括登録、スタッフ招待、複数店舗の組織管理は含めない。
Google が認めた管理権限を検証するが、利用者がオーナーか管理者かを UI で誤表示しない。

### 4.2 状態機械

`anonymous → google_connected → location_selected → line_pending → line_verified → ready → active`

分岐は `needs_google_reconnect`、`paused`、`capacity_unavailable`、`disconnected`。
未選択、LINE 未確認、規約未同意、上限未予約の状態では cron の対象にしない。
再ログインには Google の本人認証を用い、別のメールアドレスで同じ人と推定しない。

### 4.3 エラーと再開

- 権限拒否・期限切れ：理由とやり直すボタン。運営者への連絡だけを唯一の出口にしない。
- 店舗 0 件：選択中の Google アカウントを確かめる案内。API の失敗を「店舗なし」に置き換えない。
- 既登録店舗：二重登録を拒否。他利用者の名前・LINE・登録状態の詳細は返さない。
- LINE 未追加・ブロック：再追加と再テストを案内。
- 口コミ 0 件：接続成功と口コミなしを別々に表示。投稿確認まで成功したとは表示しない。
- 受付枠不足：Google の業務権限を要求する前に受付停止を表示。途中で枠が尽きた場合も明示し、自動課金しない。
- 利用停止：以後の取得・下書き・通知・承認投稿を停止。停止前に Google が受理済みの投稿は取り消せない旨を表示。
- 切断：確認画面を経て資格情報を消し、Google 側のアクセス解除方法も案内。既存の公開返信は削除しない。

## 5. 構成とデータの責任

### 5.1 配置

- 既存 Worker に `/start`、`/account`、`/api/self/*`、専用 OAuth callback を追加。
- HTML・JS・API は同一オリジン。公開サイトは入口リンクだけを持つ。ブラウザに管理キーを渡す構成にしない。
- 新しい処理を `worker/self-service/` 以下へ分離。約 1,000 行ある既存 entrypoint に認証処理を継ぎ足さない。
- Google reviews の取得・投稿、AI 下書き、LINE メッセージ生成は既存モジュールを再利用する。

### 5.2 保存

新規の自己登録領域には **Cloudflare D1** を追加する。
利用者・店舗の所有関係、OAuth state、セッション、LINE 登録コード、承認待ち、実行予約、利用量台帳をトランザクションと一意制約で管理する。
初期は read replication を有効化せず、認証・権限の判定はプライマリを使う。

最低限のエンティティ:

- `users`：Google の検証済み `sub` を安定識別子として持つ。メールは必須にしない。
- `sessions` / `oauth_attempts`：ハッシュ化したトークン、所有者、期限、認可目的、単回消費状態。
- `stores`：owner、Google location の一意識別子、表示情報、状態、LINE 通知先、世代番号。
- `google_credentials`：暗号化済み refresh token、鍵バージョン。クライアントに返さない。
- `line_links`：コードのハッシュ、store、期限、消費状態、検出した LINE 利用者。
- `review_jobs` / `replies`：元口コミ識別子、取得・生成・通知・承認投稿の状態と再試行予約。
- `usage_budgets` / `usage_reservations`：店舗別・共有チャネル別の上限、予約、消費。
- `audit_events`：誰がどの操作を行ったか。秘密値や口コミ全文は入れない。

既存の管理者登録店舗は KV のまま維持し、一括移行しない。
新規 D1 店舗を KV に二重保存しない。資格情報と権限の正本を二つ作らない。
cron と LINE 承認は保存先別のアダプタで振り分け、どちらにも本人照合を適用する。
新規処理の停止時も、既存の美容院試用経路を壊さない。

## 6. 認証・誤接続・公開投稿の安全性

- Google 接続は標準の Authorization Code / OIDC を使い、`state`、`nonce`、PKCE を検証。
  ID token は署名、issuer、audience、期限、nonce を検証するライブラリを使用し、単なる JWT decode を認証に使わない。
- 初回は `openid` と既存の `business.manage` のみ。メール・Gmail・Drive 等の不要な権限は求めない。
  再ログインは本人確認用の `openid`、再接続は業務権限を含む別 intent として扱う。
- callback の state は開始ブラウザと結び付け、D1 で期限付き・一度だけ消費。URL の storeId を信頼して他店の資格情報を書き換えない。
- セッションは高エントロピーの不透明値、DB にはハッシュ。Cookie は `HttpOnly; Secure; SameSite=Lax; Path=/`。
  初期セッションは 24 時間、再ログインで回復。state は 10 分。ログイン時にセッション ID を更新する。
- 更新 API は正しい Origin と CSRF token を必須にする。CORS の `*` と Cookie 認証を併用しない。
- 公開 API はセッションから owner を決定。`X-Admin-Key`、任意の ownerId、LINE トークンの入力を要求しない。
- 店舗の確定時と稼働開始時に、その Google 認可で対象店舗へアクセスできることを検証。
  同一 location の多重登録は D1 の一意制約で拒否する。
- 現存 KV 店舗の location は公開開始前に衝突確認用の予約だけ D1 に登録する。既存資格情報・設定は移さない。
  公開後に管理者方式で店舗を追加・選択する経路も、同じ location の予約と衝突確認を通す。
- LINE の新コードは読み間違えにくい 12 文字のランダム値、15 分、有効な発行は店舗あたり 1 件。再発行で旧コードを失効。
  新コードは既存の `MEO-xxxxxx` と区別する接頭辞を使う。平文コードをログに残さない。
- LINE Webhook は署名設定不備も拒否。1 対 1 の利用者イベントだけを登録に使い、グループには店舗を紐づけない。
  コード消費は原子的に一度だけ。さらに LINE に送る 6 桁の確認番号を、元の認証済みブラウザで照合する。
  確認番号は 5 分・最大 5 回・単回消費で、再発行時に旧番号を失効。誤った LINE を拾った場合はコードから再登録する。
  ブラウザで最終確認するまで運用を開始しない。
- **承認・スキップの両方で、LINE の userId と登録先・店舗状態・返信の所属を照合する。**
  他店の返信 ID、停止済み、再接続前の古い世代、未知 action は公開投稿せず拒否。
- Google 投稿と DB 更新を一つのトランザクションであるかのように扱わない。
  投稿前にジョブを原子的に予約し、承認済みの同じ本文だけを対象にする。ネットワーク切断で結果不明なら Google の現行返信を取得して照合してから再実行を判断する。
- HTML はエスケープ、callback の token/code は画面・ログに出さない。OAuth callback はクエリを除いた安全な画面へ redirect。
  CSP、`Cache-Control: no-store`、`Referrer-Policy: no-referrer` を認証ページへ付ける。
- 公開受付のスパム対策には Turnstile のサーバー検証、IP と利用者別の回数制限、要求サイズ制限を設ける。
  本番のキー未設定時は受付しない。テスト用キーを本番に持ち込まない。
- 旧 `/signup` は新しい公開受付の迂回路にしない。旧方式の利用状況を確認したうえで、自己登録公開モードでは旧新規登録を無効化し、新ページを案内する。
  既存の店舗レコードや管理者 API は維持する。自己登録店舗に汎用 `/review` 用キーを発行せず、下書き数制限の迂回路を作らない。

## 7. 利用枠と既存機能への接続

### 実行の上限

公開受付は feature flag で既定 OFF。必要な設定が欠けた場合は、無制限で開かず受付停止とする。
本番の公開設定として active 店舗総数、店舗別月間 AI 下書き数、共有 LINE の月間 push 予算、既存サービス用の確保枠を必須にする。
数値は本番アカウントの残量を確認してから本人承認の公開設定に固定する。未設定値は 0 として拒否する。
ローカル受入テストでは小さな明示値を fixture とし、並行要求でも上限を超えないことを検証する。

- 「LINE は無料」とは案内せず、実際の利用条件と残量を画面に表示。
- API のチャネル全体の送信数も確認する。他サービスが同じボットを使う可能性を考慮する。
- 店舗の受付枠予約、AI 生成、push 通知は D1 の原子的な予算予約を通す。予約できない処理を開始しない。
- LINE reply API と push API は別に計測し、quota 対象を取り違えない。
- LINE の quota API や送信が失敗したら安全側で停止・保留。課金プラン変更や追加購入を自動実行しない。
- 自己登録は `daily-digest` を既定にする。初回は直近 60 日の未返信から 5 件まで。残りを既読扱いにせず後続処理へ残す。
- ページング、1 回の処理件数、並列数を制限。AI や送信の失敗時に取得済みだけを根拠に口コミを処理済みにしない。
- 接続テストの再送は 1 店舗 1 分 1 回・1 日 3 回まで。自動で大量のテスト通知を送らない。
- 停止操作で将来のジョブ予約を拒否。公開投稿の直前にも稼働状態と権限を再確認する。

### 保存期間

OAuth 試行と LINE コードは期限後に削除、未完了登録の資格情報は最終操作から 24 時間で削除。
承認待ちの本文は 7 日で失効、利用者操作の監査記録は 30 日で削除。
切断確定時は新規処理を止め、関連 token と本文を削除する。公開済み Google 返信は残る。
バックアップの保持期間は本番環境の実設定を公開前に確認し、プライバシー説明に含める。

## 8. AI 向け導入案内

`docs/quickstart.md` と `docs/ai-setup.md` を同じ実装契約から整える。

AI 用ページには以下を明記:

1. 既定は共有サービスへの通常登録。開発環境の構築は不要。
2. 利用者に店舗を確認してもらい、必要な画面へ案内する。
3. Google/LINE の本人ログイン・権限確認・投稿承認は本人の操作として扱う。
4. パスワード、管理キー、refresh token をチャット・画面・ログへ貼らせない。
5. `GET /api/self/status` の秘密を含まない状態コードと、各状態の次の手順を説明。
6. 架空デモ、接続テスト、本物の Google 投稿の違いを明記。成功判定を分ける。
7. 受付停止、OAuth 設定不備、GBP API 未承認を AI が回避・なりすまし・課金で解決しない。
8. 自前運用を選ぶ場合だけ別ページへ。必要アカウント、API 承認、環境変数の名前、検証コマンド、停止方法を掲載する。

AI が使えることを理由に利用者向け画面を省略しない。AI に全権限を渡すことも導入条件にしない。

## 9. 変更対象と対象外

### 対象

- `worker/self-service/`：認証、セッション、D1 repository、状態機械、API、UI。
- `worker/index.mjs`：ルーティング、cron/LINE の保存先振り分けと必須本人照合。
- `src/`：GBP/LINE/AI の既存ロジックを必要最小限で再利用可能にし、外部 I/O をテスト差し替え可能にする。
- `migrations/`、`wrangler.toml`：ローカル D1 と安全な flag。実装計画で runtime 互換性を検証する。
- `test/` とローカル runtime/browser の専用テスト。
- `README.md`、`docs/quickstart.md`、`docs/ai-setup.md`、公開前チェックリスト。
- サイト側への入口の反映は、既存変更の担当・差分を確認した後の別統合作業。

### 対象外

- 有料課金、自動アップグレード、代理店管理、複数スタッフ管理。
- 順位計測・投稿予約・写真管理・口コミ収集キャンペーン。
- 既存店舗の一括移行、管理者招待方式の廃止。
- 利用者の全アカウントを AI が自動作成するインストーラー。
- 承認なしの本番デプロイ、記事公開、Google/LINE 設定変更。

## 10. 受入・検証

### 自動テスト

- 新規 Google 接続から店舗確定・LINE 確認・利用開始まで、管理者 API なしで完走。
- 店舗 0 / 1 / 複数、拒否、期限切れ、再ログイン、再接続、権限消失、口コミ 0 件。
- 他人の storeId/返信 ID、別 LINE、無署名 Webhook、state/nonce 改ざん、再送・多重実行を拒否。
- 同一店舗の並行登録、コード同時消費、上限直前の並行予約をローカル D1 runtime で実証。
- 投稿失敗後の再試行と、結果不明時の照合。成功と送信開始を混同しない。
- 上限到達後は AI/push が実行されず、未処理口コミが失われない。
- 停止・切断後の cron、旧 LINE ボタン、セッション、古いジョブが利用できない。
- ブラウザ API、ログ、HTML、テスト成果物に秘密が含まれない。
- 既存 Node テスト 160 件を含む全件が通り、既存管理者導入に回帰がない。

### 実利用フロー

Chrome for Testing の専用プロファイルで、スマホ幅と PC 幅の初回登録・中断復帰・エラー案内を確認する。
ローカルは架空データと Google/LINE/Groq のスタブを使い、外部送信ゼロを検証する。
スタブの成功を本番 Google/LINE の成功と呼ばない。
公開前は本人承認済みのテスト店舗・LINE 宛先で実 OAuth/接続テストを行う。
本物の口コミへの投稿は、対象と本文の本人確認後だけ行い、Google 上の反映まで確認する。

### 完了の呼び分け

- 設計完了：本書のレビュー承認。
- ローカル実装完了：自動テストとスタブ E2E 成功。
